# SPEC-006 — Raw store en Storage, ventanas por partido y tick de ingesta

## Problema
SPEC-005 dejó el contrato, el registro y un adaptador que devuelve crudo y lo
parsea, pero nadie lo llama: no hay ventana que decida a quién sondear, ni
sitio donde guardar el crudo (D-6, RN-09), ni tick que inserte Observations
respetando la cadencia (RN-08) y registrando cada intento (ADR-003). Esta spec
construye el núcleo de ingesta: raw store en Storage con retención de 30 días
(ADR-007), ventana por partido (ADR-002 §2), tick autenticado con
`ingest_attempts` (ADR-008), alerta `unresolved_team` (RN-10, ADR-006 §4) y
la columna `added_minute` que SPEC-005 dejó pendiente. Deja dos enganches
listos: `afterInsert` para el motor (spec c) y el endpoint para los
disparadores (spec d). Desglose (b) y criterios de éxito 2 y 3 de EPIC-002.

## Usuarios / roles afectados
- sdd-implementador de las specs c y d: hereda `IngestDb`, `runTick`, `RawStore`, el endpoint y la CLI; c enchufa el motor en `afterInsert`; d dispara `POST /api/ingest/tick`.
- Titular (humano): `.env` ya tiene las cinco variables (H-1); `npm run db:push` crea el bucket en `dev`; vigila el consumo de Storage en Free (N-3).
- Público y operador: ninguno todavía (nada se publica; EPIC-003/004).

## Criterios de aceptación
- **CA-1 Migraciones** (cuatro, con `supabase migration new`; `npm run db:push` las aplica y `supabase db push --dry-run --db-url "$DATABASE_URL"` no lista pendientes). (a) `added_minute`: `observations` y `decisions` ganan `added_minute integer null check (added_minute between 1 and 30)`; el CHECK `*_state_check` se recrea para exigir `added_minute is null` salvo en `live`; `observations` gana `check (raw_ref <> '')` (F-SPEC-002-7); `board` se recrea (drop + create, mismas columnas) con `added_minute` tras `minute`. (b) `ingest_attempts` gana `details jsonb not null default '{}'::jsonb` (F-SPEC-002-1). (c) Tabla `raw_purges (id uuid pk default gen_random_uuid(), started_at timestamptz not null default now(), finished_at timestamptz, ok boolean not null default false, deleted integer not null default 0 check (deleted >= 0), error text)`, índice `(started_at desc)`, RLS activado sin políticas. (d) Bucket: `insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types) values ('raw', 'raw', false, 52428800, '{application/gzip}') on conflict (id) do nothing`; ninguna política en `storage.objects`. Test (`src/db/schema.db.test.ts`, en transacción con rollback): `live` con `added_minute: 3` → acepta; `finished` con `added_minute: 3`, `live` con `0` y con `31`, `raw_ref: ''` → `23514`; `board` muestra `added_minute` de la Decision vigente; la lista de tablas gana `raw_purges` (diez); `select public from storage.buckets where id = 'raw'` → `false`; con `set local role anon`, `select count(*) from storage.objects where bucket_id = 'raw'` → 0.
- **CA-2 Raw store `src/raw/`.** `store.ts` exporta `interface RawStore { put(key, body: Uint8Array, contentType): Promise<void>; get(key): Promise<Uint8Array | null>; remove(keys: string[]): Promise<void> }` y `createStorageRawStore({ url, serviceRoleKey, bucket = 'raw', fetch })` sobre la API REST de Storage (`POST {url}/storage/v1/object/{bucket}/{key}` con `apikey: <serviceRoleKey>`, `Authorization: Bearer <serviceRoleKey>` (ambas: la clave `sb_secret_…` solo autentica por `apikey` y sin ella Storage responde `Invalid Compact JWS`, N-13), `Content-Type` y `x-upsert: false`; `GET .../object/{bucket}/{key}` (404, o 400 con cuerpo `{"statusCode":"404","code":"NoSuchKey"}`, → `null`); `DELETE .../object/{bucket}` con `{ prefixes: keys }`); toda respuesta no 2xx lanza `storage responded <status>` sin la clave. `capture.ts` exporta `rawKey(capture, attemptId)` = `<sourceId>/<YYYY-MM-DD>/<capturedAt con ':' → '-'>-<attemptId>.json.gz`, `rawRef(key)` = `raw/<key>`, `encodeCapture(capture)` = `gzipSync(JSON.stringify(RawCapture.parse(capture)))` (`node:zlib`) y `storeCapture(store, capture, attemptId): Promise<string>` (devuelve el `raw_ref`). `env.ts`: `rawStoreEnv(env)` lee `NEXT_PUBLIC_SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY` y lanza nombrando la que falte. - **CA-6 Puerto `src/ingest/db.ts`.** `interface IngestDb { windowMatches(now): Promise<(WindowMatch & { status: MatchStatus })[]>; openAttempt(sourceId, now, minIntervalSeconds): Promise<{ id: string } | { skipped: 'cadence'; lastStartedAt: Instant }>; closeAttempt(id, { finishedAt, ok, error?, rawRef?, observations, details }): Promise<void>; transaction<T>(fn: (tx: IngestTx) => Promise<T>): Promise<T>; lastPurge(): Promise<{ startedAt, ok } | null>; openPurge(now): Promise<string>; closePurge(id, { finishedAt, ok, deleted, error? }): Promise<void>; staleRawKeys(before, limit): Promise<string[]> }` e `interface IngestTx { insertObservations(observations: Observation[]): Promise<void>; openUnresolvedAlerts(sourceId, rawRef, items: Unresolved[]): Promise<number>; sql: TransactionSql }`. `createIngestDb(sql)`: `windowMatches` consulta `board` por `kickoff` entre `now − 150 min` y `now + 10 min` y filtra con `isInWindow` (instantes convertidos a `Instant` en esta capa; ningún `Date` sale de ella); `openAttempt` en una transacción con `pg_advisory_xact_lock(hashtext('ingest_attempts:' || sourceId))`: si el último `started_at` de la fuente es posterior a `now − (minIntervalSeconds − CADENCE_JITTER_SECONDS)` devuelve `skipped`, si no inserta y devuelve `id`; `insertObservations` inserta con `id` explícito y `added_minute` solo en `live`; `openUnresolvedAlerts` inserta `alerts (kind 'unresolved_team', match_id null, details { sourceId, rawRef, reason, externalCompetition, externalMatchId, home, away, status })` salvo que exista una sin resolver con el mismo `details->>'sourceId'` y `details->>'externalMatchId'` (N-8) y devuelve cuántas abrió; `staleRawKeys` = `select name from storage.objects where bucket_id = 'raw' and created_at < before order by created_at limit n`. Test `src/ingest/db.db.test.ts` (local): partido sembrado con `kickoff = now` aparece en `windowMatches`; con Decision `finished` no; con `kickoff = now + 11 min` no; `openAttempt` a `now` → `id`, a `now + 20 s` → `skipped` con `lastStartedAt`, a `now + 26 s` → `id`; dos `openAttempt` concurrentes (`Promise.all`, fuente `test-<uuid>`, filas borradas al final) → exactamente un `id`; `insertObservations` de un `live` con `addedMinute: 3` → `added_minute = 3` y de un `finished` → `null`; `openUnresolvedAlerts` con el mismo item dos veces → 1 fila; dos objetos insertados en `storage.objects` (`raw`, `created_at` a −31 y −1 días) → `staleRawKeys(now − 30 d)` devuelve solo el viejo.
- **CA-7 Tick `src/ingest/tick.ts`.** `runTick({ db, store, sources, adapterFor, fetch, now, afterInsert? }): Promise<TickSummary>` con `TickSummary = { now, inWindow, purge: 'skipped' | 'ran' | 'failed', attempts: AttemptSummary[] }` y `AttemptSummary = { sourceId, season, attemptId?, skipped?: 'cadence', ok, error?, rawRef?, matches, requests, observations, unresolved, skippedItems, alerts }`. Orden: purga (CA-8) → `windowMatches(now)` → si está vacía termina sin tocar `adapterFor`, `fetch` ni `openAttempt` (RN-08, criterio 2) → agrupa por `season` → por cada fuente `pull` de `sources` (orden del registro) y temporada con partidos de sus `competitions`: `openAttempt` (cadencia → `skipped`, sin `fetch`) → `adapter.fetch({ now, competitions: <las que tienen partidos>, matches, fetch, userAgent: config.userAgent })` → `storeCapture` **antes** de `parse`; si `fetch` o `storeCapture` lanzan, `closeAttempt(ok: false, error)` y no se parsea (D-6) → `parse` (lanza → `closeAttempt(ok: false, error, rawRef)`) → `Observation[]` con `id: crypto.randomUUID()`, `sourceId`, `observedAt = parsed.observedAt ?? capture.capturedAt`, `receivedAt = now`, `rawRef`, validadas con `Observation.parse` (SPEC-005 N-1) → una `db.transaction`: `insertObservations`, `openUnresolvedAlerts`, `afterInsert?.(tx, observations)` (N-11) → `closeAttempt(ok: true, rawRef, observations: n, details: { season, matches, requests, unresolved, skipped, alerts })`. El fallo de una fuente no detiene a las demás (ADR-003); un fallo de `transaction` cierra el intento con error. Test `src/ingest/tick.test.ts` (`IngestDb` y `RawStore` en memoria, adaptador stub, `fetch` que lanza si se le llama): ventana vacía → `inWindow: 0`, `attempts: []`, cero llamadas a `adapterFor`/`openAttempt`; dos partidos de dos competiciones → el adaptador recibe exactamente esos y esas competiciones, `userAgent` del registro y `now`; el log de llamadas muestra `put` antes de `parse`; `parse` con 1 observación + 1 `unresolved` + 1 `skipped` → 1 Observation con `rawRef` = el devuelto por `storeCapture`, `observedAt = capturedAt`, `receivedAt = now`; 1 alerta; intento `ok` con contadores; `fetch` del adaptador lanza → intento `ok: false` con `error` y la segunda fuente corre igual; `put` lanza → `parse` no se llama (spy) y no hay observaciones; `parse` lanza → intento con `error` y `rawRef`; `afterInsert` recibe las observaciones dentro de la transacción (el `IngestDb` en memoria registra `begin`/`commit` y la llamada queda entre ambos); `openAttempt` → `skipped` → sin `fetch` y `skipped: 'cadence'` en el resumen; dos temporadas en ventana → dos intentos de la misma fuente.
- **CA-8 Retención `src/ingest/purge.ts`.** `purgeRaw({ db, store, now })`: `lastPurge()` con `ok` hace menos de `PURGE_EVERY_HOURS`, o cualquiera hace menos de `PURGE_RETRY_HOURS` → `'skipped'`; si no, `openPurge(now)` y bucle `staleRawKeys(now − RAW_RETENTION_DAYS, PURGE_BATCH)` → `store.remove(keys)` hasta lista vacía → `closePurge(ok: true, deleted)` → `'ran'`; un error cierra con `ok: false`, `error` y lo borrado hasta entonces → `'failed'`, y `runTick` continúa. ## Notas para el gate humano
Decisiones fijadas por Alberto Fojo en el gate (2026-09-21); aprobación formal pendiente.
- **H-1 (precondición, asumida).** `.env` tiene `DATABASE_URL`, `API_FOOTBALL_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` e `INGEST_TICK_TOKEN` (SPEC-001 CA-12); el titular confirma que el token tendrá ≥ 32 caracteres y que `npm run db:push` puede crear el bucket `raw` en `dev`. La verificación en ventana real cae el viernes 2026-09-25 desde 18:30Z: hasta entonces se verifica fuera de ventana y con dobles.
- **H-2 (decidido).** El fixture `live-<fecha>.json` de las cinco ligas (SPEC-005 CA-7 (iii), F-SPEC-005-1) **no entra aquí**: queda como residual de SPEC-005 con destino en la spec d (jornada de medición), que es la que necesita datos live reales. CA-11 es estricto: ningún diff en `src/sources`.
- **N-1 Puerto `IngestDb`** (ADR-008 §5): el tick se prueba en CI con dobles porque `test:db` es solo local (SPEC-002 N-7). La implementación real se prueba en `db.db.test.ts`. Coste: una interfaz más; beneficio: EPIC-004 reutiliza `IngestTx`.
- **N-2 Tolerancia de 5 s en la cadencia (decidido, ADR-008 §3).** Con guarda estricta a 30 s, un disparo 1 s adelantado saltaría la fuente y la cadencia efectiva oscilaría entre 30 y 60 s. RN-08 se lee como «no más a menudo que la cadencia declarada, con el jitter del disparador»; el peor caso son dos peticiones a 25 s. El registro sigue en `minIntervalSeconds: 30`; SPEC-005 no se toca.
- **N-3 Un objeto por captura, gzip** (ADR-007 §2): estimación ~20-30 MB por día de jornada; 30 días < 1 GB de Storage en Free. Aceptado: el titular vigila el panel de Supabase a mano en la primera jornada; si se acerca al límite, Supabase `prod` (Pro) adelanta o se abre ADR.
- **N-4 Purga dentro del tick (decidido, ADR-007 §5)**, una vez cada 24 h, en vez de endpoint + job diario: la retención es automática en cuanto el tick corre y la spec d no programa nada más. Coste: una vez al día un tick tarda ~1-2 s más.
- **N-5 Alias por `node:fs` + tracing** (ADR-008 §8) en vez de import estático o tabla: sin código por temporada, sin esquema nuevo. Riesgo: si el tracing falla en Vercel, el intento falla con `no alias for …` (visible en `ingest_attempts.error`); CA-4 lo verifica en el `.nft.json` del build.
- **N-6 Sin ventana no hay fila** en `ingest_attempts` (ADR-008 §4): ~2.880 filas/día sin dato si no. La vitalidad fuera de ventana la observa la spec d en logs y `cron.job_run_details`.
- **N-7 Solo `POST` (decidido).** Vercel Cron invoca por `GET` con `Authorization: Bearer $CRON_SECRET`: la spec d decide si exporta `GET` con la misma guarda o una ruta `/api/cron/tick` que delega. Aquí el núcleo (`createTickHandler`) no depende del método.
- **N-8 Deduplicación de `unresolved_team`** por `(sourceId, externalMatchId)` abierta: un equipo sin alias generaría una alerta cada 30 s durante 160 min. Con `externalMatchId` nulo no se deduplica (no hay clave).
- **N-9 `ingest_attempts.details` jsonb** con contadores (`season, matches, requests, unresolved, skipped, alerts`) en vez de cinco columnas: la spec d añadirá latencias sin migración. Ajusta F-SPEC-002-1.
- **N-10 Observaciones fuera de ventana se insertan** si `parse` las devuelve con `matchId` del calendario (p. ej. `live=` trae un partido cuyo kickoff declarado está mal): la ventana limita peticiones (RN-08), no verdades. FK de `matches` protege.
- **N-12 Borde del reloj `src/clock.ts`** (refinamiento del 2026-09-21, F-SPEC-006-3): CA-9 decía `new Date()` en `handler.ts` y CA-11 exige que nada bajo `src/ingest/` ni `src/raw/` lea el reloj. Se resuelve con `nowInstant()` en `src/clock.ts`, fuera de ambas carpetas: el handler y la CLI lo llaman y `now` viaja como `Instant`. Precisa ADR-008 §7 («`now` lo pone la ruta o la CLI») sin alterarlo: la ruta sigue poniéndolo, a través de `src/clock.ts`. CA-11 no cambia.
- **N-13 Cabecera `apikey` y `NoSuchKey`** (precisiones a ADR-007 §4, F-SPEC-006-1 y F-SPEC-006-2): la clave de servicio de Supabase en formato `sb_secret_…` no es un JWT; la API REST de Storage la rechaza con `Invalid Compact JWS` si solo va en `Authorization: Bearer` y exige además `apikey`. Un objeto inexistente responde 404 o HTTP 400 con `{"statusCode":"404","code":"NoSuchKey"}`; el store trata ambos como `null`. La decisión de ADR-007 (REST con la clave de servicio, sin `supabase-js`) no cambia; ADR-007 es inmutable por estar aprobado y estas precisiones viven aquí.
